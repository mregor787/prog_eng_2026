# Проектирование схемы MongoDB

В базу данных MongoDB было решено перенести сущность **User**. Две другие сущности (**Parcel** и **Delivery**) было решено оставить в реляционной базе данных PostgreSQL, поскольку они требуют строгой консистентности, транзакционности и активно используют реляционные связи. 

Преимущество такого разделения основывается на документной модели MongoDB, которая хорошо подходит для пользовательских профилей, при этом транзакционная часть сохраняется в реляционной БД.

## Коллекция: `users` (Пользователи)

Коллекция хранит профили пользователей системы доставки.

```json
{
  "_id": Int64,
  "login": String,
  "email": String,
  "password_hash": String,
  "first_name": String,
  "last_name": String,
  "created_at": Date,
  "preferences": {
    "language": String,
    "notifications_enabled": Boolean
  },
  "statistics": {
    "sent_parcels": Int,
    "received_parcels": Int
  }
}
```

### Обоснование Embedded Documents vs. References

- `preferences` - Embedded Document. 

Настройки пользователя являются небольшой структурой, всегда загружаются вместе с профилем и не используются отдельно от пользователя. Использование embedded document уменьшает количество запросов, упрощает чтение профиля и соответствует document-oriented модели MongoDB.

- `statistics` - Embedded Document.

Статистика пользователя представляет собой агрегированные данные (количество отправленных и полученных посылок). Эти данные принадлежат только пользователю, обновляются вместе с профилем и не требуют отдельной коллекции. Поэтому embedded document является оптимальным решением для нее.

## Почему Parcel и Delivery остались в PostgreSQL

Сущности **Parcel** и **Delivery** тесно связаны друг с другом, требуют внешних ключей (Foreign Key) и строгой консистентности данных. PostgreSQL лучше подходит для таких задач благодаря своей реляционной модели, поддержке ACID-транзакций и эффективной работе со связями.
