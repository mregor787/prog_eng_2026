# Стратегии кэширования и Rate Limiting

## Анализ производительности и Hot Paths

В ходе анализа системы доставки были выявлены следующие высоконагруженные и потенциально медленные операции:
- **`GET /api/v1/parcels` (parcel-service)** - получение списка посылок текущего пользователя. Запрос может вызываться часто при открытии личного кабинета или обновлении интерфейса. Требует обращения к PostgreSQL и сортировки по `created_at`.
- **`GET /api/v1/deliveries?sender_id=...` и `GET /api/v1/deliveries?receiver_id=...` (delivery-service)** - получение списка отправленных и полученных доставок. Является одним из основных пользовательских сценариев и потенциально создает высокую нагрузку на БД при большом количестве доставок.
- **`POST /api/v1/auth/login` (user-service)** - endpoint аутентификации. Подвержен brute-force атакам и флуду запросами.

### Требования к производительности

Для пользовательских API были определены следующие целевые показатели:

| Метрика | Целевое значение |
|---|---|
| Среднее время ответа (cached) | < 10 ms |
| Среднее время ответа (DB query) | < 100 ms |
| P99 latency | < 300 ms |
| Пропускная способность | > 100 RPS |
| Время ответа login endpoint | < 50 ms |

## Стратегия кэширования

Для уменьшения нагрузки на PostgreSQL был внедрен Redis в роли распределенного in-memory кэша. 

Используется стратегия **Cache-Aside (Lazy Loading)**:

1. Handler сначала пытается получить данные из Redis.
2. При cache miss выполняется запрос к PostgreSQL.
3. Полученный результат сериализуется в JSON и сохраняется в Redis с TTL.

### Кэшируемые данные

| Endpoint | Данные | Ключ в Redis | TTL | Стратегия инвалидации |
|---|---|---|---|---|
| `GET /api/v1/parcels` | Список посылок пользователя | `parcels:user:{user_id}` | 60 сек | Явная инвалидация при создании новой посылки |
| `GET /api/v1/deliveries?sender_id=...` | Список отправленных доставок | `deliveries:sender:{sender_id}` | 60 сек | Явная инвалидация при создании новой доставки |
| `GET /api/v1/deliveries?receiver_id=...` | Список полученных доставок | `deliveries:receiver:{receiver_id}` | 60 сек | Явная инвалидация при создании новой доставки |

## Стратегия Rate Limiting

Для защиты API от brute-force атак и чрезмерной нагрузки реализован алгоритм **Fixed Window Counter** на базе Redis.

### Алгоритм работы
1. Для каждого клиента в Redis хранится счетчик запросов.
2. Каждый запрос выполняет операцию INCR.
3. При первом запросе устанавливается EXPIRE.
4. Если количество запросов превышает лимит - сервер возвращает 429 Too Many Requests.

### Используемый endpoint

| Endpoint | Ключ ограничения | Лимит | Окно | Ответ при превышении лимита |
|---|---|---|---|---|
| `POST /api/v1/auth/login` | Client IP | 10 req | 60s | `429 Too Many Requests` |

### Ключ в Redis

`login:{client_ip}`

### HTTP-заголовки

При каждом запросе endpoint возвращает:
- `X-RateLimit-Limit` - максимальное количество запросов.
- `X-RateLimit-Remaining` - оставшееся количество запросов.
- `X-RateLimit-Reset` - количество секунд до сброса окна.

## Метрики эффективности

Для оценки эффективности кэширования и rate limiting используются следующие метрики:

### Метрики кэширования

| Метрика | Описание |
|---|---|
| Cache Hit Rate | Доля запросов, обслуженных Redis |
| Cache Miss Rate | Доля запросов, потребовавших обращение к PostgreSQL |
| Redis Memory Usage | Объем памяти Redis |
| Average Cached Response Time | Среднее время ответа из кэша |

### Формула hit rate

`Cache Hit Rate = hits / (hits + misses)`

### Метрики rate limiting

| Метрика | Описание |
|---|---|
| Blocked Requests Count | Количество запросов, отклоненных RL |
| Login Request Rate | Частота login запросов |
| Redis Counter Count | Количество активных RL ключей |

## Влияние оптимизаций на систему

### Кэширование

Использование Redis позволяет:

- значительно сократить количество обращений к PostgreSQL;
- ускорить обработку популярных GET-запросов;
- уменьшить нагрузку на CPU и disk I/O PostgreSQL;
- обслуживать повторяющиеся запросы полностью из RAM.

### Rate Limiting

Rate limiting позволяет:

- ограничить brute-force атаки на login endpoint;
- предотвратить перегрузку backend-сервисов;
- уменьшить количество вредоносных запросов;
- защитить PostgreSQL от избыточной нагрузки.

### Отказоустойчивость

Реализация использует подход fail-open:

- при недоступности Redis сервис продолжает обрабатывать запросы;
- кэширование и RL считаются дополнительными оптимизациями, а не критически важной частью бизнес-логики.
